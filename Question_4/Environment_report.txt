4. Output and Error Redirection
--------------------------------------------------
Command:
echo "Normal output" > out.txt
cat out.txt

ls /nonexistentfolder 2> err.txt
cat err.txt

badcommand123 > both.txt 2>&1
cat both.txt

Output:
Normal output
ls: cannot access '/nonexistentfolder': No such file or directory
badcommand123: command not found

Observation:
The three redirection operators behaved exactly as expected: > out.txt sent
standard output ("Normal output") into a file, overwriting any prior
content. 2> err.txt captured only the standard error stream from the failed
ls command ("No such file or directory") while leaving stdout untouched.
Finally, > both.txt 2>&1 merged stderr into the same destination as stdout,
so the "command not found" error from the invalid command badcommand123 was
captured in both.txt even though it was technically an error message. This
demonstrates that Linux treats stdout and stderr as two completely separate
streams that can be redirected independently or combined.

6. Explanation: How Linux Manages File I/O
--------------------------------------------------
Linux follows the principle that "everything is a file" — regular files,
directories, devices, pipes, and sockets are all accessed through a uniform
file descriptor interface. When a process opens a file, the kernel assigns
it a small integer (the file descriptor) that indexes into a per-process
file descriptor table; this table in turn points to a system-wide open file
table, which references the underlying inode holding the actual data. Every
process starts with three descriptors already open — 0 (stdin), 1 (stdout),
and 2 (stderr) — normally connected to the controlling terminal, as
confirmed by our /proc/self/fd output. Shell redirection operators (>, 2>,
2>&1) work by rewiring these descriptors to point at files instead of the
terminal before the program even starts executing, which is why a program
itself doesn't need to know whether its output is going to a screen or a
file. Finally, the kernel enforces resource limits (via ulimit) on a
per-process and per-user basis — such as the maximum number of open file
descriptors — to ensure no single process or user can exhaust shared system
resources and destabilize the machine.
