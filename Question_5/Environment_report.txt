Observation:
The root filesystem (/dev/sdd) has just over 67 million inodes available,
with only 49,630 currently in use — an inode utilization of just 1%. This
means the system is nowhere near running out of the ability to create new
files, even though a filesystem can theoretically run out of inodes before
it runs out of raw disk space, especially in scenarios with millions of
very small files (e.g., logging-heavy applications).

--------------------------------------------------
5. Storage Health Observations
--------------------------------------------------
- Disk usage on the root filesystem is very low at 1%, so there is no
  immediate capacity concern for the Linux environment itself.
- Inode usage is also low at 1%, meaning the filesystem is nowhere near
  running out of inodes despite having over 67 million available.
- The Windows C: drive (mounted at /mnt/c) is heavily used at 88%, which is
  worth monitoring since it is close to running low on space, even though
  it sits outside the Linux filesystem being assessed.
- No filesystem relevant to the new application server deployment is near
  capacity; storage health is currently good.

--------------------------------------------------
6. Recommendations for Improving Storage Utilization
--------------------------------------------------
- Set up periodic cleanup of logs and temporary files (e.g., in /var/log
  and /tmp) to prevent gradual buildup over the server's lifetime.
- Monitor inode usage on any filesystem expected to store many small files
  (such as application logs or session data), since inode exhaustion can
  block new file creation even while disk space remains available.
- Keep an eye on the Windows host's C: drive (currently 88% full), since
  low space on the host can indirectly affect WSL2 performance and
  available virtual disk growth.
- Before deploying the new application server, allocate a dedicated
  filesystem/partition for application data and logs, separate from the OS
  partition, so usage can be monitored and scaled independently.
- Consider setting up automated disk usage and inode monitoring/alerts
  ahead of production deployment, rather than relying on manual checks.
